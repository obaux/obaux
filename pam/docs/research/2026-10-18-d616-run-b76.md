## Findings, all polish

| # | Lane | What |
|---|---|---|
| D1 | Nico / Lena | **The database checks the route and the action by shape, not by the list.** A direct call stored `/aaliyah-smith/` as a route. A lowercase name would pass as an action (`aaliyah.smith`). The app never sends either, so this needs someone calling `report_app_error` by hand, and it can't hold a number or an `@`. Lena's rules 2 and 3 say a pattern and a closed list. A table of the actions, or the list in the function, closes it. |
| D2 | Nico | **A server error with no database code is logged as `unknown`, not its status.** A 500 with only a message became `unknown`, because PostgREST's error object carries no HTTP status and `codeFromError` sees none. The plan and the closed list include HTTP statuses, so the Problems list loses the most useful code for a server fault. |
| D3 | Nico | **A report that gets a 5xx with an empty body is treated as "not reached" and stays at the head of the queue.** It's sent again with the next failure, and the newer report waits behind it. If the first actually landed (a gateway timing out after the insert), it's logged twice. If the endpoint keeps failing, only the head is ever tried. Treating any HTTP answer as reached (as a coded refusal already is) would end both. |
| D4 | Lena | **The account id is kept for up to ten minutes in `app_error_limits`** (bucket `u:<uuid>`), for the per-account limit. It's swept every 5 minutes on live (`sweep-app-error-counters`). It isn't in the log itself, but the Privacy line about the error log may want to say so, or the bucket could be a hash of the id. Lena's call. |
