# D-616 — A failed action writes an error log the team is told about

**Date:** 2026-10-18 · **Branch:** `claude/messages-app-errors`

**Decided by:** Will, 18 October 2026, 21:14, to the merge desk: "...if something breaks, please create an error log so the team can be notified and fix the issue." It goes with his new pattern for a failed action (a small alert at the bottom of the screen, Dot's `useMalfunction()`). The Privacy rules are Lena's read (`docs/legal/2026-10-18-error-log-privacy-read.md`, section 3), taken by the merge desk at 21:23.

## What

- **`public.app_errors`** holds one row per reported failure: when, the route **as a pattern** (`/person/[id]/`, never an id or a query), a stable **action key** from a closed list (`alerts.switch.closed`), a **code** (an HTTP status, a Postgres SQLSTATE, or `offline` / `timeout` / `unknown`), the build, the platform, the role the person was acting as, and the language. **No free text at all.** An error's own message carries the value that broke it (`Key (phone)=(...) already exists`), so there is no detail column and the function takes no detail. No account id, phone, message text or place name: no column holds one, and the route, key and code are held to a narrow shape by the table's own checks. The role is read from the person's sign-in inside the function, so a screen cannot claim one.
- **Inserts go only through `report_app_error(area, action, code, build, platform, locale)`**, a security definer function (`search_path = public, extensions`) callable signed in, signed out, and by an Edge Function through the service role. It never raises for a bad value (a report must not break the screen that sent it): a code that is not an HTTP status, a SQLSTATE or one of the three words becomes `unknown`; the route loses its query and any id (uuids and long digit runs become `[id]`); a junk build, platform or language becomes empty or `unknown`. A report whose **action is not shaped like a stable key is refused and writes nothing**.
- **The closed list of actions is in the app's code** (`packages/config/src/appErrors.ts`, `APP_ERROR_ACTIONS`), checked against the database's shape by `app-errors.test.ts`; the client drops a key that is not on it. The database holds only the SHAPE of a key, not the list: a list in the database would need a migration every time a screen gained an action that could fail. A key can still be wrong (a legal one for something that did not happen), but it cannot carry what a person typed.
- **Only a super admin reads it; nobody writes it but the function.** RLS is on and forced. `anon` has no grant. `authenticated` has `select` through a policy that asks `is_super_admin()`, so a member, a case manager and a program lead each get nothing, and nobody has a write grant. The counters table has no grant at all.
- **A switch, `app_errors_live`, starts `off`.** With it off the function writes nothing, not even a counter, and the client does not call it. Turned on by the merge desk only after Lena's Privacy line is signed by Will.
- **A rate limit:** ten reports a minute per caller (the account, else a one-way hash of the network address, counters kept an hour), sixty for the service role, two hundred a minute overall.
- **The team is told once an hour per action, in the app and nowhere else.** The first time an action fails in an hour, every super admin gets one bell row (`app_error`, `notify.app_error`, `{action, count}`) holding nothing the log row does not; later failures of that action in the hour raise the count and make no new row. No email, chat or outside service: that would be a new host and a new Privacy sentence. Ava builds the list they open; the bell line needs Sage.
- **Thirty days, enforced:** `sweep_app_errors()` deletes rows older than `app_errors_keep_days()` (one function that says 30, so the number is in one place), the old counters and the old bell rows, nightly at 04:20.

## What a later session might reverse

- The action list lives in code, not in the database. If a key is ever wrongly accepted that carries something it should not, move the list into a table and make the function check it.
- Will may choose a week instead of thirty days: change `app_errors_keep_days()` and Privacy's line together.

**Proof:** DB test 85. Each guard was put back broken and the matching check failed: the read policy (a member selecting got rows), the code check, the route's id scrub, the action shape. Also: switch off writes nothing; anon and authenticated cannot write; a member, a case manager and a program lead read nothing and a super admin reads rows; an error's own words come out as `unknown`; a route with an id and a query is stored as a pattern; no stored column holds the phone, email, first name or street fed to it; the rate limit; the bell once an hour with its count and only for super admins; the service role; the sweep keeps 29 days and removes 31. Unit test `app-errors.test.ts` holds the closed list to the database's key shape.
